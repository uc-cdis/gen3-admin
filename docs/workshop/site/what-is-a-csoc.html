What is a CSOC?

The terms, the purpose, who a CSOC suits, and the people involved in running one.

Gen3 and data commons

A data commons is a shared platform where a research community stores, describes, finds and analyzes data, with access controlled per user and per project. Gen3 is open-source software for building data commons, developed by the Center for Translational Data Science (CTDS) at the University of Chicago and published on GitHub under the uc-cdis organization. A Gen3 commons runs as a set of Gen3 services on Kubernetes. The Gen3 documentation describes them.

The CSOC

CSOC stands for Cloud Services Operations Center. It is a control plane: the CSOC portal, its API and a Keycloak sign-in service, running in their own Amazon EKS cluster in your AWS account. From the CSOC you deploy Gen3 commons, configure them and keep track of them.

  • It deploys commons through agents. An agent is a small program that runs in a Kubernetes cluster, connects out to the CSOC, and carries out the CSOC's instructions there. To install a commons, the CSOC tells the agent to run Helm, the package manager for Kubernetes applications. The first cluster is the CSOC's own.
  • It provides sign-in. Each commons can sign users in through the CSOC's Keycloak, so one identity setup serves every commons. What each user may do in a commons is set by that commons' user.yaml, a file that lists users by email and the permissions each one has.
  • It keeps a record. Every environment and every change is recorded in an S3 state bucket in your account, alongside the Terraform state.

The bootstrap wizard is a separate tool that runs on your computer, not in AWS. It creates the CSOC, and you use it again for the CSOC's own maintenance: changing the allowed addresses, upgrading the CSOC portal, resetting the administrator password and tearing down. Gen3 commons are managed from the CSOC portal. Keep the wizard's prerequisites, and access to the state bucket and the AWS account, for as long as the CSOC runs (see Plan who keeps access).

Why an institution would use one

  • Several commons, one way of running them. Groups that host commons for several labs, consortia or projects deploy each one the same way, from one place.
  • Your account, your data. Everything runs in an AWS account your institution owns, under your institution's agreements and controls.
  • One sign-in setup. Keycloak can be connected to your campus identity provider once, and every commons uses it. See Connect your institution's sign-in.
  • Reviewable changes. The wizard shows the Terraform plan before it changes anything.

Is this right for you?

A CSOC is a good fit if all of these are true:

  • You expect to run more than one Gen3 commons, or to offer commons as a service to research groups.
  • You can get a new AWS account with no other workloads, and administrator rights in it.
  • You can get a DNS subdomain delegated to that account (see Request DNS delegation).
  • Someone on your team can read Terraform plans, Kubernetes logs and AWS bills.

Choose differently, or plan extra work, in these cases:

  • You need a single commons only. Installing the Gen3 Helm chart (gen3-helm) into an existing cluster is simpler.
  • You will hold controlled-access, regulated or protected health data. Before you store such data, your security team must review the setup and harden it. Start with What this setup is not.
  • You cannot use AWS. The bootstrap creates AWS resources only.

Roles

At a university these roles are usually different people; at a small institute one person may hold several.

RoleResponsibilities
Operator (research-computing engineer)Completes the prerequisites, runs the bootstrap wizard, operates the CSOC, deploys commons, and tears environments down.
Owner (service or project lead)Decides to adopt, owns the AWS account and its budget, and approves what data the commons may hold.
Security and compliance reviewerReviews the architecture, the access model and the data classification before real data arrives. Start at Security, cost and responsibilities.
Cloud account administratorsProvide the AWS account and the administrator role, and set any organization-wide policies (Service Control Policies).
DNS administrators (often central IT)Delegate a subdomain of the institution's domain to the CSOC's account.
Commons administratorsManage users and permissions within each commons, through its user.yaml.
