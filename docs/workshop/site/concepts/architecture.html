Architecture

What runs where, in detail: the wizard on your computer, the AWS credentials it uses, the state bucket, the network and cluster, and everything the bootstrap installs.

Read this page to know what you are operating and reviewing: which component does what, where it runs, and what it can reach. The tutorial pages link here for detail; procedures are in the tutorial and the how-to guides.

The bootstrap wizard on your computer

docker-compose.workshop.yml starts three long-running containers from published images. (docker-compose-bootstrap-csoc.yml builds the same containers from source, for development.)

ServiceBuilt fromListens onRole
frontendquay.io/cdis/csoc-bootstrap-frontend (Next.js)127.0.0.1:3000Serves the wizard at /bootstrap and forwards /api calls to the API.
apiquay.io/cdis/csoc-api (Go)127.0.0.1:8002Acts with your AWS credentials, without a sign-in of its own, and starts runner containers.
docker-proxytecnativa/docker-socket-proxyan internal network onlyGives the API the container and image operations the runner needs (CONTAINERS, IMAGES and POST enabled) and blocks the rest of the Docker API.

For each run (init, plan, apply, bootstrap, finish, uninstall and destroy) the API starts a new runner container from the image in TERRAFORM_RUNNER_IMAGE, quay.io/cdis/csoc-terraform:feat_csoc-bootstrap-wizard, which contains Terraform, Helm, kubectl and the AWS CLI. The runner is started through your computer's Docker, so the paths it mounts are paths on your computer: ~/.aws, the run working directories under ~/.gen3-csoc/terraform, and the runner scripts from the repository. The runner's log streams back to the page while it runs.

Loopback only

The API runs in a mode that skips sign-in, so anything that can reach it acts as an administrator with your AWS credentials. Both services are published on 127.0.0.1 only. Do not change that, and do not run the wizard on a shared machine.

AWS credentials

With Select AWS profile the wizard uses your profiles and asks for no keys; only Provide credentials manually takes keys. Your SSO sign-in authenticates the <your-sso-profile> profile; the <your-aws-profile> profile can assume an administrator role in the CSOC's account on top of it. The API mounts ~/.aws so that an SSO token can be refreshed. Each runner gets AWS_PROFILE=<your-aws-profile> and a private, writable copy of ~/.aws, so that the AWS CLI can refresh a token without changing your files.

Inside the cluster, nothing uses your credentials. Each controller and the CSOC API reach AWS through their own IAM role for service accounts (IRSA), and each role allows only what that component needs.

State bucket and registry

One S3 bucket, gen3-csoc-csoc-dev-111122223333, holds the Terraform state for each environment (the S3 backend, locked with an S3 lock file rather than a DynamoDB table) and the registry: one record per environment and one per run. The wizard's banner, and later the CSOC portal, read the same records. The bucket is created with versioning, encryption, TLS-only access and public access blocked.

text
s3://<state-bucket>/
  gen3-csoc/environments/<csoc-name>/
    environment.json      the environment record: settled status, last run, settings
    terraform.tfstate     the Terraform state, with a lock file beside it during a run
    runs/<id>.json        one record per run: operation, status, plan summary
    runs/<id>.log         the run's log

A plan's summary (addresses, types, actions and names) is stored with its run; the full plan, which contains your settings, stays in the run's working directory on your computer.

Network and outbound traffic

The Terraform configuration is gen3-terraform's examples/csoc, which uses its vpc and eks modules (uc-cdis/gen3-terraform). A plan on a new account creates about 120 resources.

ComponentDetail
VPCThree availability zones, CIDR 172.24.16.0/20 by default, with public and private subnets and route tables. See Amazon VPC.
Internet and NAT gatewaysIn the public subnet. See NAT gateways.
SquidAn outbound proxy (Squid) in an auto-scaling group, on Amazon Linux 2023. The cluster's private subnets have no route to the internet of their own; everything the cluster fetches passes through Squid, which allows only listed destinations.
Route-check functionAn AWS Lambda function, gw_checks, in a small subnet (int_services) that reaches AWS through the NAT gateway. It finds a healthy Squid instance, points the private subnets' default route at it, and names it cloud-proxy.internal.io in a private Route 53 zone.
LogsTwo CloudWatch log groups: one named after the CSOC (for example csoc-dev), which keeps logs for 3653 days by default, and one for the route-check function, which keeps them for 14 days. VPC flow logs are off by default (vpc_flow_logs = false).

The cluster's public outbound address is therefore that of the Squid instance in use. The bootstrap records it and adds it to the allowlist. If Squid is replaced, the address changes, and the bootstrap and the finish must run again to allow the new one.

The EKS cluster

ComponentDetail
Control planeAmazon EKS running Kubernetes 1.33, which is past EKS standard support. It has a private API endpoint and a public one with no CIDR restriction (see Internet-facing endpoints). Creating it takes about 10 minutes.
IAMThe cluster's OIDC provider, and IRSA roles for the AWS Load Balancer Controller, External Secrets Operator, the EBS CSI driver, the CSOC API and external-dns. Terraform creates only these roles; the controllers themselves, including the EBS CSI driver, are installed by the bootstrap with Helm. An EKS access entry gives the deploying role administrator access to the cluster.
KarpenterKarpenter runs on AWS Fargate. When pods cannot be scheduled, it starts on-demand amd64 EC2 nodes running Amazon Linux 2023, choosing the cheapest instance type that fits from any family of generation 5 or newer (karpenter_instance_categories = [], karpenter_min_instance_generation = "4"). The first node joins in under 1 minute. The cluster has no fixed node group.

The ACM certificate, the hosted zone and the state bucket are not part of the Terraform configuration: the wizard creates them (the configuration is applied with create_certificate = false).

Certificates and DNS

  • The wizard creates the hosted zone csoc.example.org with a 60-second negative-caching time, so that a lookup made before a record exists is not remembered for long. It refuses to delegate a name that already has records in the parent zone.
  • On the Certificate step, the wizard requests an ACM certificate for the portal and Keycloak hostnames and writes its DNS validation records into the zone. You can import a certificate or choose an existing one instead.
  • The finish creates the two hostname records. For each commons, the CSOC requests a certificate and external-dns publishes the hostname, writing only records it owns (marked with TXT records), and never the CSOC's own two hostnames.

What the bootstrap installs

The bootstrap runs scripts/runner/install-csoc.sh, and direct.sh for the direct mode. It installs each component with Helm under the release name and namespace an Argo CD application would use.

With With a GitOps repo, the bootstrap installs External Secrets Operator and Argo CD with a root application instead, and opens a pull request with the CSOC's configuration. Argo CD installs the rest once the pull request is merged, and every later change to the CSOC is a pull request.

What the finish does

  1. Applies Keycloak's and the portal's ingresses again, with your addresses and the cluster's outbound address on the allowlist.
  2. Waits until Keycloak is ready and the portal's Helm release has rolled out.
  3. Waits until the csoc-realm import is done, then deletes csoc-admin-bootstrap. From then on only Keycloak holds the administrator password.
  4. Waits for the load balancer and reads its hostname.
  5. With a Route 53 zone, creates or updates two CNAME records with a 60-second TTL, for portal.csoc.example.org and auth.csoc.example.org, pointing at the load balancer. Without one, it prints the records for you to create.

Sign-in sessions in the CSOC realm last up to 12 hours and end after 8 hours without activity. The realm is created with these settings, and the wizard checks them each time its Done step loads.

Sign-in

The portal signs users in with OpenID Connect. Keycloak returns the browser to the portal with a one-time code, and the portal exchanges the code for tokens by calling Keycloak's public hostname from inside the cluster. That call leaves through Squid, which is why the cluster's outbound address must be on the allowlist. Keycloak's users, clients and sessions live in its PostgreSQL database in the cluster.

Agents

  • Pressing Deploy Agent calls the CSOC API (POST /api/agents/local). The API issues a client certificate from the CSOC's own certificate authority, renders the agent's manifest (a Deployment running quay.io/cdis/csoc-agent, its ServiceAccount and the certificate Secret) and applies it to its own cluster.
  • The agent connects to the CSOC's gRPC endpoint and keeps the connection open. In the CSOC's own cluster that is csoc-grpc.csoc.svc:50051. Both sides present certificates (mutual TLS).
  • The same endpoint is also exposed through an internet-facing Network Load Balancer on port 50051, limited to the allowlist, for agents outside the cluster. Connecting an agent from another cluster is listed in Known gaps.

Deploying a commons

  • Request a certificate makes the CSOC API request an ACM certificate for the commons hostname and write its validation records into the zone, using the API's IAM role.
  • Use CSOC login creates a Keycloak client named fence-<namespace> in the CSOC realm and fills in Fence's generic OIDC settings with it.
  • Deploy Gen3 sends the values you changed to the CSOC API (POST /api/agent/<cluster>/helm/install), which forwards the install to the agent. The agent runs helm install for the chart gen3 from https://helm.gen3.org (gen3-helm).
  • The commons' ingress becomes a load balancer with the certificate, and external-dns publishes its hostname with a TXT ownership record.

Teardown

The uninstall (scripts/runner/uninstall-csoc.sh) runs before terraform destroy, in this order:

  1. The Squid route-check function is deleted, so that it stops rewriting cloud-proxy.internal.io and the private subnets' routes.
  2. Argo CD, if installed, then every ingress and LoadBalancer service, so that the load balancer controller deletes the load balancers and their security groups.
  3. The CSOC portal, Keycloak and its database, then every namespace except the cluster's own, including commons. external-dns removes the commons' records as their ingresses go. Orphaned webhooks and leftover finalizers are removed.
  4. Every persistent volume and Karpenter's nodes. With Force, EBS volumes are deleted by ID and instances are terminated instead of drained.
  5. The CSOC's two hostname records, Squid's private record, and the secrets under gen3-csoc/<csoc-name>/, deleted without a recovery window.

Then terraform destroy runs (after an init) and removes the cluster, Fargate and Karpenter, the IAM roles, Squid, the NAT gateway and the VPC. The optional zone deletion removes the zone, the CSOC's certificate and the NS records in the parent; the optional bucket deletion runs last.
