# CSOC workshop docs (static site)

A multi-page technical walkthrough of the CSOC hands-on workshop: from an
empty AWS account to a running CSOC, a Gen3 commons on it, and the teardown.
It is generic: written for any reader in their own AWS account. It was made
from the one-page workshop guide in `../guide/index.html`, which stays as it is.

Plain HTML, one stylesheet and one script. No build step, no external network
or CDN. It works when opened from disk (`open index.html`) and when served by
GitHub Pages as-is.

```
site/
  .nojekyll              tells GitHub Pages not to run Jekyll
  index.html             Overview
  prerequisites.html     Before you start: what to decide, tools, AWS credentials, domain
  start-the-wizard.html  setup.html  review-and-provision.html  plan.html
  apply.html  certificate-and-dns.html  install.html  finish.html  sign-in.html
  connect-cluster.html  deploy-gen3.html  teardown.html
  reference/             architecture, wizard-states, troubleshooting,
                         glossary, where-things-live
  assets/site.css        all styles (light/dark, mobile, print)
  assets/site.js         navigation, search (index embedded), timers, diagrams
  assets/img/            the screenshots the pages use (copied from ../img/)
```

All links are relative, so the site works at any URL path
(`https://<org>.github.io/<repo>/`, a subfolder, or `file://`).

## Publish with GitHub Pages

GitHub Pages' "Deploy from a branch" source only serves the repository root
(`/`) or `/docs`. This site lives in `docs/workshop/site/`, so pick one of the
two options below.

### Option A: deploy from a branch (no workflow)

1. Put the site where Pages can serve it: either copy the contents of
   `docs/workshop/site/` into `/docs` on a branch (for example a dedicated
   `gh-pages` branch, so `/docs` on `master` is untouched), or copy them to the
   root of that branch.
2. On GitHub: **Settings → Pages → Build and deployment → Source: Deploy from
   a branch**. Choose the branch and the folder (`/` or `/docs`), then **Save**.
3. Keep `.nojekyll` next to `index.html` in the published folder.
4. After a minute the site is at `https://<org>.github.io/<repo>/`.

Re-copy the folder whenever the docs change.

### Option B: deploy with a GitHub Actions workflow

Publish `docs/workshop/site/` directly, with no copy kept in git:

1. On GitHub: **Settings → Pages → Build and deployment → Source: GitHub
   Actions**.
2. Add a workflow (not included here) that, on pushes touching
   `docs/workshop/site/**`, runs `actions/checkout`, then
   `actions/configure-pages`, `actions/upload-pages-artifact` with
   `path: docs/workshop/site`, and `actions/deploy-pages`. It needs
   `permissions: pages: write, id-token: write` and the `github-pages`
   environment.
3. The site is at `https://<org>.github.io/<repo>/`.

## Features, briefly

- Left navigation with the current page marked, breadcrumbs, previous/next
  links, and an "On this page" table of contents with scroll-spy.
- Search (press `/`) over every section of every page. The index is a JSON
  array embedded in `assets/site.js` (`var IDX = [...]`), so it needs no server.
- **Placeholders**: nothing is pre-filled. Wherever a command or field needs
  the reader's own value it shows a placeholder such as `<your-domain>` or
  `<your-aws-profile>`; the Prerequisites page lists them all under "What
  you'll need to decide". Examples use `example.org`.
- Light/dark theme (follows `prefers-color-scheme` until you choose), copy
  buttons on code blocks, anchored headings (click `#` to copy a link),
  admonitions, optional per-step timers (kept in localStorage), a mobile layout with a collapsible
  sidebar, and a print stylesheet (sidebar and controls hidden, diagrams shown
  complete, folded sections opened).
- Animated SVG diagrams with Play/Pause/step controls. They start complete and
  only animate when you press Play; with `prefers-reduced-motion` the flowing
  and pulsing effects are off.

## Editing

The pages are generated by the scripts in `../site-src/` (see its README):
edit the page sources there and run `node build.mjs`, which rewrites the HTML,
rebuilds the search index inside `assets/site.js` and copies the screenshots.
`assets/site.css` is not generated; edit it here directly. Publishing needs no
build: the generated files are committed as they are.

If the app and these docs disagree, the app is right.
