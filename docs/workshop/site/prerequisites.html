Prerequisites

Everything to do before you open the wizard, with a worksheet for every value it asks for.

Time 10–30 minutes, plus any wait for DNS delegation

Before you open the wizard, do four things:

  1. Fill in the worksheet below.
  2. Install Git, the AWS CLI version 2 and Docker, and pull the wizard's images.
  3. Create an AWS CLI profile, and confirm that aws sts get-caller-identity prints the ID of the account the CSOC goes in.
  4. Get your subdomain, for example csoc.example.org, delegated to that account, or send the request to central IT.

The hostname decides the zone

The wizard takes the hostname and drops its first label to get the zone: portal.csoc.example.org gives csoc.example.org. A hostname with only three labels, such as portal.example.org, makes the zone portal.example.org itself, which is not what you want. Always use a hostname with a label in front of your subdomain.

Choose the Region before you create the bucket

Create bucket creates the bucket in the Region currently selected under AWS Region, which is us-east-1 until you change it. On the Setup step, AWS Region comes after CSOC Name, below the bucket field, so set it first.

Steps

Install the tools and pull the images

  1. Terminal Install Git.
  2. Terminal Install the AWS CLI version 2. You use it to sign in; the runs use their own copy inside the runner image.
  3. Terminal Install and start a Docker runtime: Docker Desktop, OrbStack or Colima, with Docker Compose. Check that Docker is running: docker info --format '{{.ServerVersion}}'
  4. Terminal Clone the repository:
    bash
    git clone https://github.com/uc-cdis/gen3-admin
cd gen3-admin
  5. Terminal Pull the wizard's images. They are published, so nothing is built on your computer:
    bash
    docker compose -f docker-compose.workshop.yml pull
docker pull quay.io/cdis/csoc-terraform:feat_csoc-bootstrap-wizard
    The second command pulls the runner image, which the wizard starts for every run.

The wizard's images run only on your computer. docker-compose.workshop.yml pins them all to the tag feat_csoc-bootstrap-wizard:

ImagePurpose
quay.io/cdis/csoc-api:feat_csoc-bootstrap-wizardThe wizard's API.
quay.io/cdis/csoc-bootstrap-frontend:feat_csoc-bootstrap-wizardThe wizard's web pages.
quay.io/cdis/csoc-terraform:feat_csoc-bootstrap-wizardThe runner: Terraform, Helm, kubectl and the AWS CLI.
tecnativa/docker-socket-proxy:v0.5.0The restricted Docker socket proxy.

The runner fetches the CSOC's Terraform from gen3-terraform's feat/csoc-bootstrap-master branch (set by TERRAFORM_MODULES_REF in the compose file). The repository checkout is still needed: the runner mounts its scripts/runner and helm/csoc directories. To build the images from source instead, see For developers.

The images that run in your AWS account are listed in Images and pinning.

Create an AWS CLI profile

The wizard reads the AWS CLI's profiles from ~/.aws on your computer. It also offers Provide credentials manually, where you paste access keys into the page; use Select AWS profile instead, so that no keys are typed into a browser.

  1. Get the account. Ask your cloud administrators for a new AWS account with no other workloads, and an administrator role in it, such as one with the AdministratorAccess policy. The bootstrap creates IAM roles and policies, a VPC, an EKS cluster, EC2 instances, an AWS Lambda function, load balancers, Route 53 records, ACM certificates, Secrets Manager secrets and S3 buckets, so a narrower role fails part-way. Why administrator rights explains this for your reviewers.
  2. Terminal Create the profile.
    • If your institution signs in to AWS through IAM Identity Center (AWS SSO), which is recommended, run aws configure sso as described in Configuring IAM Identity Center authentication with the AWS CLI, and name the profile, for example csoc-admin.
    • If you sign in to one account and assume a role in the CSOC account, add a second profile like this to ~/.aws/config, where <your-sso-profile> is the profile you sign in with:
      ini
      [profile <your-aws-profile>]
role_arn = arn:aws:iam::<account-id>:role/<admin-role>
source_profile = <your-sso-profile>
region = <your-region>
    • If you use access keys, put them in a named profile in ~/.aws/credentials.
  3. Terminal Sign in and check the account:
    bash
    aws sso login --profile <your-sso-profile>
aws sts get-caller-identity --profile <your-aws-profile>
    The Account value must be the ID of the CSOC account, for example 111122223333. If you use access keys, skip aws sso login. In these docs, <your-sso-profile> is the profile you sign in with; if that sign-in lands directly in the CSOC account, it is the same profile as <your-aws-profile>.

Check the account number

If the number is not the CSOC account, fix the profile before you continue. Default credentials can point at another account, such as the one that holds your institution's DNS.

Sign in shortly before you start

The wizard asks you to sign in again before an apply or a teardown if less than 45 minutes are left on your SSO sign-in, and before a bootstrap or a finish if less than 15 minutes are left.

Get your subdomain delegated

The wizard creates a Route 53 hosted zone for your subdomain in the CSOC account. Delegation is one NS record set in the parent domain's zone, listing the new zone's four name servers, so that the internet finds the new zone. ACM needs it before it can issue a certificate (DNS validation). Find out where example.org is hosted, then follow the matching branch:

Where the parent domain isChoose on the Setup stepWho adds the delegationLead time
In Route 53, in the CSOC accountThe credentials above (the default)The wizardNone
In Route 53, in another account you have a profile forProfile: followed by that profile's name, for example Profile: dns-adminThe wizardNone
Managed by central IT, in Route 53 or elsewhereI'll add the NS records myselfCentral IT, from your request (template)Days, at most universities. Send the request now.

If your institution will not delegate a subdomain at all, choose I manage DNS myself on the Setup step instead and add each record by hand; see Use DNS you manage yourself.

Plan who keeps access

You use the wizard for the CSOC's whole life: changing the allowed addresses, upgrading the CSOC portal, resetting the administrator password and tearing down all run from it. Each needs the repository, Docker, and a profile with administrator rights in the account; the wizard reads everything else from the state bucket. Make sure two people on your team can do this, and include it in any handover when the operator changes.

Expected result

  • git --version and aws --version print versions.
  • docker info prints a version, not "Cannot connect to the Docker daemon".
  • docker images lists quay.io/cdis/csoc-api, quay.io/cdis/csoc-bootstrap-frontend and quay.io/cdis/csoc-terraform with the tag feat_csoc-bootstrap-wizard.
  • aws sts get-caller-identity --profile <your-aws-profile> prints the CSOC account's ID.
  • Every row of the worksheet has a value, and the delegation is in place or requested.

What's happening

The wizard works entirely from your computer with your AWS credentials. Terraform, Helm, kubectl and a copy of the AWS CLI are in the runner image, and the wizard starts one runner container for each run.
